# Локальный бенчмарк offload для llama.cpp

Стандартный Python без сторонних зависимостей. Скрипт предназначен для будущих измерений внутри Linux/WSL с уже установленными исполняемым файлом llama.cpp, GGUF-моделью, необязательным проектором и файлом промпта. Он ничего не загружает и не устанавливает, не открывает сетевые соединения и не меняет настройки системы или WSL. По умолчанию формируется только план: модель не запускается.

## План без запуска модели

```sh
python3 scripts/bench-offload/bench_offload.py \
  --binary /path/to/llama-cli --model /path/to/model.gguf \
  --projector /path/to/mmproj.gguf --prompt /path/to/prompt.txt \
  --product-root /path/to/product-root
```

Проектор необязателен. Результат создаётся в уникальном каталоге `bench-results/<run-id>/`; даже первый запуск не использует сам `bench-results/`. Существующие каталоги результатов не перезаписываются. Можно указать `--output` с новым внешним каталогом.

Матрица разделяет число слоёв весов на GPU (`-ngl`), размещение KV (`--kv-offload` или `--no-kv-offload`) и тип K/V кэша (`f16`, `q8_0`, `q4_0`). Матрица по умолчанию содержит 6 случаев (один слойный уровень × два варианта KV × три типа KV). Расширение через `--layers` явно задаёт до четырёх уникальных чисел, максимум 24 случая; контекст ограничен верхним пределом runner. По умолчанию используется 128 генерируемых токенов и таймаут 120 секунд; значения можно явно увеличить параметрами `--tokens` и `--timeout` в пределах hard caps. Контекст, `-b 512`, `-ub 128`, single-turn режим и sampler фиксируются и записываются в плане. sampler: seed 42, temperature 0. Для промпта используется его точный текст; скрипт не задаёт собственный шаблон чата. Перед запуском проверяются `--help` и `--version` именно локального бинарного файла; неизвестные флаги не приводят к запасному режиму.

## Явный запуск позднее

Фактические тесты на целевом Windows/WSL компьютере отложены. Перед будущим запуском нужны локально подготовленные файлы, внешняя изоляция сети и заполненный оператором ledger. Пример:

```sh
python3 scripts/bench-offload/bench_offload.py \
  --binary /path/to/llama-cli --model /path/to/model.gguf \
  --prompt /path/to/prompt.txt --product-root /path/to/product-root \
  --ledger /path/to/product-ledger.json \
  --context 4096 --tokens 256 --repeats 1 --timeout 600 \
  --output /path/to/product-root/bench-results/run-001 --run
```

Ledger имеет явную аддитивную основу `external_only`. Формула исключает двойной счёт: если product root расположен внутри внешнего контейнера/VHDX, укажите `root_container_key`; тогда один раз учитывается `max(логический размер root, выделенный размер контейнера)`. Если root отдельно, учитываются его логические байты. Затем прибавляются остальные не перекрывающиеся внешние выделения, дополнительный пик обновления/восстановления и зарезервированный максимум логов/результатов. Размеры модели и проектора обязательны как информационные поля, но не прибавляются повторно: они уже находятся либо в product root, либо внутри перечисленного внешнего выделения. Если указан полный размер VHDX, файлы внутри него нельзя перечислять повторно. VHDX, содержащий product root, указывается через `root_container_key` и учитывается вместе с root один раз по максимуму логического/выделенного размера. Скрипт сверяет `model_bytes`/`projector_bytes` с размерами поданных файлов, требует размер внешней allocation не меньше их суммы и проверяет, что resolved-пути соответствуют заявлению `model_projector_location`. Для файлов вне root укажите `inside_external_allocation` и `model_projector_allocation_key`, который ссылается на запись внешнего ledger; фактическое включение этих файлов в контейнер подтверждает оператор.

Пример схемы:

```json
{
  "complete": true,
  "accounting_basis": "external_only",
  "product_root": "/path/to/product-root",
  "external_allocations_bytes": {"product-vhdx": 50000000000, "separate-runtime-image": 123456789},
  "root_container_key": "product-vhdx",
  "overlap_exclusions": ["files_within_vhdx", "overlapping_host_guest_views", "product_root_overlap"],
  "model_projector_location": "inside_product_root",
  "model_bytes": 123456789,
  "projector_bytes": 0,
  "update_peak_bytes": 1000000000
}
```

Предел проекта — ровно 100 000 000 000 десятичных байт. `complete: true` — утверждение оператора, а не автоматическая проверка полноты. Обход product root видит логические размеры и не доказывает физическое выделение VHDX, перекрытие host/guest или дедупликацию. Поэтому `certified_pass` всегда `false`, даже если расчёт ниже предела. Неизвестные host-side счётчики отмечаются отдельно. Свободное место диска гостя проверяется отдельно и не подменяет общий бюджет.

Перед каждым случаем и во время него скрипт проверяет доступную RAM гостя и свободное место гостевого диска. Проверки опрашиваются примерно каждые 0,25 секунды; резкий скачок использования между опросами может превысить порог до реакции. Файл каждого лога ограничен лимитом ОС, общий объём логов — 64 MiB; суммарный предел может быть превышен максимум на лимит одного активного файла. Guards и счётчики гостя проверяются примерно каждые 0,25 секунды; семплы RAM/RSS/свободного места сохраняются не чаще раза в секунду. Рост записи результатов ограничен 8 MiB, число сохранённых семплов — 20 000. При ошибке/прерывании сохраняются план, статус и доступная частичная информация. При отказе или таймауте завершается только группа процессов текущего дочернего запуска.

Показания `nvidia-smi` — только наблюдение, не VRAM-защита. Автоматических guard-проверок Windows host RAM/disk нет: их нужно проверять вручную до запуска. Для гостя и host нельзя складывать значения RAM. Это не OS sandbox и не защита от мгновенного OOM; внешняя изоляция сети обязательна. Настоящий TTFT недоступен: stdout-first-byte не измеряется как TTFT, соответствующее поле остаётся `null`. Сохраняются wall time и строки внутренних perf-таймингов llama.cpp, если они присутствуют.

Для разработки проверяются только синтаксис, режим плана и синтетические исполняемые заглушки в `/tmp`; реальные измерения модели на целевом Windows/WSL отложены.
