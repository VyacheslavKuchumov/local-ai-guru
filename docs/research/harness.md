# Harness security and local isolation fact collection

**Research date:** 2026-10-28. The sources below are upstream/official documentation checked on that date. This is a fact collection, not a stack recommendation. No target Windows machine or runtime was available for local measurements; all performance, compatibility, and policy-effectiveness claims remain unmeasured locally.

## Minimal harness boundary

The harness should own explicit, default-deny decisions outside model output: network mode (`offline` at startup; only an explicit user action can enable it), allowed destination set, readable/writable filesystem roots, and callable tools. A model response is data; it must not be able to grant itself permissions. Keep policy evaluation in the trusted host/harness, and mediate every operation through it. A UI toggle alone is not an OS security boundary.

The smallest conceptual surface is:

| Capability | Harness policy | Boundary needed for hostile code / process escape |
|---|---|---|
| Network | Default off; explicit session-scoped enable; configured host/domain allowlist | OS firewall/WFP or a constrained proxy/network namespace applied to all relevant processes. A process-local HTTP client filter is insufficient. |
| Files | Canonical allowed roots, operation-level read/write checks; separate generated-output area | Run with a restricted OS identity/container and only expose those roots. Resolve/recheck paths at use time and reject link/reparse-point escapes. |
| Tools | Fixed registry, per-tool schema/argument validation, user authorization for consequential actions | Do not give model-generated text to a shell. If execution is a product feature, isolate the child process and its inherited handles, environment, working directory, and OS permissions. |

This layer can reduce accidental exposure and constrain normal tool calls. It cannot by itself contain arbitrary native code, a compromised runtime, or a child process that inherits broader OS privileges. Windows AppContainer is documented as a process isolation boundary with separately granted filesystem, network, and process capabilities; whether the chosen desktop app and dependencies can run there is unverified. Source: [Microsoft: AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation).

## Network: offline default, scoped allowlist

- `llama-server` documents a default listen address of `127.0.0.1:9931`, but accepts a configurable host; binding to `0.0.0.0` exposes it on interfaces. The Docker example explicitly uses `--host 0.0.0.0`. Keep local API binding loopback-only unless remote clients are a deliberate feature; do not treat loopback as authenticated or safe from other local processes. Source: [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Windows Firewall allows outbound traffic by default unless a blocking rule matches. Microsoft documents FQDN dynamic keywords, but calls them an aid to managing changing IPs, not a secure DNS service; resolution uses the endpoint's configured DNS, and proxies, secure DNS, VPN configurations, and cached IPs limit coverage. Therefore domain rules alone do not establish a robust domain allowlist against direct-IP, alternate-DNS, proxy, or child-process paths. Source: [Windows Firewall dynamic keywords](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/dynamic-keywords) and [Firewall rule configuration](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure).
- A workable policy needs a clear enforcement point for all egress, including child processes: either OS-level default-deny rules covering the application/process tree (and any execution broker), or a mandatory proxy with direct egress blocked. A host allowlist must define exact names, subdomains/wildcards, ports, protocols, redirect behavior, and whether IP literals are forbidden. DNS answers and redirects must be checked at connection time; checking only an initial URL is not sufficient. These are design requirements/inferences; no implementation has been validated.
- If using a proxy, prevent bypass by blocking direct network access for the app and all children. Validate each redirect target against policy and avoid treating a previously allowed hostname as permission for a new destination reached via redirect. DNS rebinding and IP-literal cases require address-level controls as well as hostname checks. Windows FQDN keyword documentation explicitly notes cached-IP and proxy limitations; exact protections for a future proxy remain to be selected and tested.
- Docker's `--network none` gives a container only loopback, according to Docker docs. This is a strong container-level offline option if llama.cpp is run inside that container, but doesn't establish a host application's egress policy. Conversely, bridge/port-published containers and Docker Desktop's VM/network plumbing need separate review. Source: [Docker: none network driver](https://docs.docker.com/engine/network/drivers/none).
- Windows Sandbox is not offline by default: networking and clipboard redirection are enabled in its default configuration. A `.wsb` file can disable networking and configure mapped folders, but any mapped host folder is a deliberate bridge. Source: [Microsoft: Configure Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file).
- Model switching must have explicit memory ownership: unload/terminate the previous model process and clear session state, prompt buffers, tool results, and any model-specific KV/cache state before assigning a new model/session. Separate per-session memory from shared durable knowledge and make any persistence explicit. This is a harness requirement, not something established by the llama.cpp docs; local lifecycle behavior remains unverified.

## Filesystem and process/tool boundaries

- Maintain a normalized root allowlist and enforce it on every open, create, rename, delete, and export. String-prefix checks are not a containment check. Windows NTFS supports symbolic links and junctions/reparse points; a path that appears beneath an approved root may resolve elsewhere. Resolve the final target and reject traversal across the boundary, including races between checking and opening. Sources: [Microsoft: hard links and junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions), [Microsoft: reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points).
- A container is only as narrow as its mounts. Docker documents bind mounts as read-write by default and warns that processes in a container can modify host files through them; read-only mounts are available. Mount only required roots, read-only where possible, and account for nested mounts. Source: [Docker: bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).
- Tool allowlisting belongs in trusted harness code: expose named operations, validate structured arguments and sizes, apply path/domain checks after parsing, and require confirmation for side effects. Prompt injection can occur in retrieved documents or tool output; the model may be induced to request an otherwise registered tool. Treat retrieved text as untrusted data, do not let it alter policy, and keep authorization checks outside prompts. These are security requirements; no prompt-injection defense is claimed as complete.
- Never concatenate model-controlled arguments into a shell command. Prefer direct executable invocation with a fixed executable path and separately passed, validated argument vector; quote/escape alone is not an authorization boundary. Do not execute generated code by default. If enabled later, run it as a low-privilege child under the same network/filesystem/tool restrictions, with resource/time limits and no inherited secrets or handles. Exact Windows process/job-object containment and required access controls remain to be researched and tested before implementation.

## llama.cpp-specific network and API surface

- Current upstream server documentation describes model-management endpoints in router mode: `POST /models` starts a model download; `DELETE /models` removes cached model data. It also documents `-hf`/`--hf-repo`, `--model-url`, and Docker repository model sources. Do not expose those endpoints or remote model-source flags in an offline product profile; deny download routes at the server boundary and provide only locally staged GGUF paths. Source: [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Upstream docs also describe optional server tools that provide filesystem access to the Web UI (`--tools all` or named tools). Keep server tools disabled unless individually reviewed; a separate harness allowlist is preferable to implicitly enabling all server-side tools. Same source above.
- Server API key support or loopback binding does not enforce outbound network allowlists, filesystem roots, or tool policy. Any local API endpoint should be loopback-bound, inaccessible to untrusted LAN clients, and protected from other local clients as needed. Reachability, authentication defaults, and endpoint set vary by build/version and require validation against the pinned binary.

## Verified facts vs. gaps

**Verified from remote primary documentation:** Windows Sandbox defaults to networking enabled; Windows Firewall's default outbound behavior is allow unless blocked; FQDN dynamic keywords have documented DNS/proxy/cache limitations; AppContainer has capability-based file/network/process isolation; Docker `--network none` is loopback-only; Docker bind mounts are writable by default; NTFS junctions and reparse points exist; llama.cpp documents a loopback server default, configurable host, model-download management API, remote model-source flags, and optional filesystem tools.

**Not measured or verified locally:** Windows edition/build and availability of Sandbox/AppContainer features; GPU/CPU effect or llama.cpp behavior inside isolation; process-tree firewall coverage; egress blocking for child processes; DNS/redirect/IP-literal enforcement; local API exposure/auth behavior for a pinned release; filesystem escape resistance under symlinks/junction races; model unload/session-memory cleanup; offline startup and absence of auto-download attempts. No models, corpora, or large assets were downloaded.

## Open questions for design follow-up

1. Which isolation mechanism can be shipped and supported on the target Windows editions without relying on Docker/WSL or a VPN?
2. What exact allowlist syntax and scope does the user-facing explicit network-enable command accept, and how are redirects, DNS changes, IPv6, and proxies handled?
3. Will generated code execution exist at all? If so, which Windows identity/container boundary, resource limits, and child-process egress controls are available?
4. Which llama.cpp release/build is pinned, and how will router/download/tool endpoints and local API access be disabled or constrained in that exact build?
5. What tests will prove process-tree egress denial, path containment across junctions, and memory cleanup during model switching on the actual Windows machine?
