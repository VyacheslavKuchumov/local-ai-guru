# Большие модели, RAM offload и будущий стенд — 28.10.2026

Статус: исследование первоисточников и подготовка воспроизводимого опыта. Пользователь подтвердил возможность Windows-тестов **позже**; сейчас target access отсутствует. Ни одна цифра ниже не является локальным inference benchmark. Облачная работа агентов разработки не измеряет локальную модель продукта. Требования: WSL-first, offline default, без VPN/системных изменений; 1–2 человека, один активный запрос. A1 Qwen3.5-9B и A2 Gemma 4 E4B остаются обязательным сравнением.

Новый жёсткий бюджет продукта — **100000000000 bytes = 100 GB ≈93.13 GiB**, без уже установленной Windows, со всеми данными продукта, WSL overhead, моделями/проекторами, средами/зависимостями, оригиналами, индексами, журналами, restore copies и временным пиком. Это ограничение дизайна, не доказанная вместимость. Подробная ведомость и квоты — ARCHITECTURE.md §7. RAM offload не увеличивает дисковый бюджет.

## Три независимых рычага

Проверенные current upstream определения: [common argument implementation](https://github.com/ggml-org/llama.cpp/blob/master/common/arg.cpp), [server reference](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), доступ 28.10.2026. Перед исполнением приоритет имеет `--help` **локального закреплённого бинарника**, затем startup allocation logs. Новые flags не приписываются старой сборке.

| Рычаг | Что менять в отдельном опыте | Что это не доказывает |
| --- | --- | --- |
| Веса на CPU/RAM | Фиксированное числовое `-ngl` / `--n-gpu-layers`, уменьшение GPU layers при неизменных ctx/cache types | Остаток не становится бесплатным: CPU-resident tensors, mmap/page cache и buffers требуют RAM и CPU работы; может ухудшиться prompt/decode latency |
| Живой KV на CPU/RAM | `--no-kv-offload` при тех же weights placement и f16 cache | Не перенос всех весов в RAM. Высвобождает только реально GPU-resident KV; CPU attention/трафик/синхронизация могут дать большую задержку. Hybrid recurrent state учитывать отдельно |
| KV precision | `-ctk` и `-ctv`, отдельно f16 → q8_0 → q4_0 при фиксированном placement | Не quant весов GGUF и не гарантия поддержки данного architecture/backend/Flash Attention. Снижение памяти/качество измеряются, не выводятся из flags alone |

`--cache-ram` — idle prompt-state cache, не рычаг размещения живого KV. Для матрицы — один процесс/slot, фиксированные ctx, layers, batch/ubatch, template/thinking, seed и output limit. `--fit off`, если локальный help поддерживает; unsupported build/case — `not run`/ошибка, не silent fallback. Upstream fit/router оценивает host RAM как unlimited и может не учитывать projector; его estimate не является safety gate для 16 ГБ. Отдельный `--no-mmproj-offload` — только дополнительный vision-опыт при поддержке и собственной строке результата.

Пример **расчёта, не модели**: обычный transformer с 32 attention layers, 8 KV heads, head_dim128, K+V и f16 при 8192 tokens: `32×8×128×2×2×8192 =1073741824 bytes` (1 GiB). При 4K это 0.5 GiB; реальная quant упаковка имеет overhead. Qwen3.5/3.6 hybrid с recurrent state и Gemma hybrid/sliding/global layers не заменяются этим примером. Их KV allocation берётся из startup logs выбранной сборки; zero/неизвестный counter не выдумывается.

## RAM, WSL и задержка

VRAM gate: `GPU weights + GPU KV + projector/image state + compute buffers + display reserve ≤ measured free/total`. Guest RAM gate: `CPU weights + CPU KV/recurrent state + host buffers + guest services/cache ≤ guest limit`, одновременно Windows должен сохранять согласованный Available RAM запас. Guest memory уже входит в Windows physical usage; нельзя сложить 16 ГБ RAM +12 ГБ VRAM и назвать 28 ГБ доступным для произвольного размещения.

Illustrative M1 feasibility: если после резервов под Windows/display/guest/buffers останется около 8 GiB для GPU weights и 6 GiB для CPU weights, это всего 14 GiB для весов, меньше M1 Q3 +projector 15.142 GiB ещё до дополнительного KV. Это показывает напряжённость, **не замер и не доказательство невозможности**. Реальное распределение не линейно числу layers; P1 сначала снимает фактические allocation logs. Увеличить WSL memory на бумаге недостаточно: отнимается запас Windows, а CPU KV конкурирует с CPU weights.

[Microsoft WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), проверка 28.10.2026, описывает default memory 50% Windows RAM и disk-backed swap. Фактические version/config/guest limit проверить; на данной машине ничего не менять. При близком к default лимите RAM offload может упереться в guest раньше host RAM. Swap/pagefile — расход диска и источник возможных stalls, не дополнительная пригодная RAM; его фактическое product allocation входит в 100GB. Не выполнять shutdown, compaction, cache dropping или изменение memory/swap автоматически.

Предварительная RAM trial matrix, не настройка сейчас: сначала WSL ceiling `memory=8GB`, затем отдельный согласованный опыт `memory=10GB` для offload при закрытых тяжёлых Windows приложениях. 12GB не является default для host16ГБ. Ceiling не означает немедленное резервирование всего объёма; фактические guest/host bytes измеряются. В обоих опытах требовать наблюдаемый Windows Available RAM запас (исходная инженерная гипотеза ≥2 GiB) и контролировать его во время нагрузки; при нехватке — остановить опыт, не увеличивать лимит автоматически. Внутри guest считаются Linux/services +CPU weights +CPU KV/recurrent state +buffers; тяжёлая dev сборка одновременно не запускается. Смена memory/swap — отдельная будущая явная операция, никаких правок конфигурации или shutdown сейчас. Swap stalls фиксируются как ресурсный недостаток, не как успешная пригодность.

Честная latency-гипотеза: partial weights и CPU KV могут позволить загрузку, но ухудшить TTFT/prompt processing/decode; короткий успешный prompt не означает пригодность длинного диалога. Измерять code/RU/tool/vision качество рядом с speed/resource results. Не обещать tokens/s или секунды без target. `mmap` размер и process RSS не равны полной Windows commit/guest residency; медленные page faults при memory pressure учитываются отдельно. Отсутствующие host/GPU counters помечаются unavailable, без притворного pass.

## Ограниченный контракт будущего опыта P1-O

Предусловия: A1/A2 завершены, target Windows доступен позднее, разрешены конкретные локальные артефакты, работают guest/host network/file gates, полный disk ledger/ресурсный baseline известны. L1 первый; L2 только при необходимости; M1 — сначала Q4 budget gate; его непрохождение даёт not-run, а Q3 требует отдельного optional решения и сравнения с меньшей моделью Q4/Q5, не одновременно с L1/L2; D3.8 после M1 только при обосновании, без обязательства скачать оба больших кандидата. Нет загрузок сейчас. GPU/CPU weights и KV сравнивать на **одном** разрешённом файле, чтобы не расходовать диск на множество quants.

1. Read-only inventory: Windows/distro/driver/runtime version, guest limit/MemAvailable, Windows Available RAM, free VRAM, WSL VHDX allocated bytes и host free bytes, active services. Сохранить hard limit100000000000 и полную ledger coverage.
2. Dry-run строит command matrix и peak budget без model launch. 2K/4K ctx для первоначального большего кандидата, output≤128, один repeat и timeout≤120s на разведку. До 8K/512 output/трёх repeats переходить лишь после успешного gate; общая серия ограничена временем/выводом и числом cases.
3. W0: фиксированный GPU layers/ctx/f16 KV. W1: меньше GPU layers с тем же KV. K1: тот же ngl/ctx, KV CPU/f16. K2: тот же GPU placement, KV q8_0. K3: q4_0 только после K2. Не смешивать все переменные в одном шаге; неподдержанный hybrid/FA case сохраняется rejected/not-run и не переписывается в f16. Exact layer counts и FA mode из локального help/metadata; automatic fit не меняет matrix.
4. При low guest RAM/disk, disk peak>100GB, неполном обязательном accounting, timeout или log cap runner останавливает свой процесс/группу и записывает причину/partial samples. Windows Available RAM и VRAM запас — внешние/ручные prerequisites и контроль оператора: raw nvidia-smi observation не является автоматическим VRAM guard. При нарушении этих условий оператор прекращает опыт; runner не объявляет их проверенными. Sampled guards не являются OS hard memory limit и не предотвращают мгновенный OOM.
5. Сравнить одинаковые fixtures и процессные allocation logs, elapsed, prompt/gen timings; CLI runner сохраняет wall time и доступные perf lines, настоящая TTFT здесь unavailable/null и требует позднее отдельной надёжной token stream instrumentation. Даже при появлении stdout-first-byte proxy он **не TTFT**. Результат — pass/fail/not-run + raw evidence; unload подтверждается завершённым PID, не только текстом ответа.

До целевого запуска сейчас допустимы только syntax, dry-run и synthetic stub smoke tests runner. `scripts/bench-offload/` принадлежит единственному writer offload-runner; Planner интегрирует документы и читает/проверяет результат. Поздние результаты сохраняются в уникальном `bench-results/<run-id>/` или external directory; каталоги с моделью/cache не чистятся, существующий результат не перезаписывается. Runner не доказывает sandbox/сеть runtime и не сертифицирует полный VHDX budget одним обходом product root; полная ведомость внешних host allocations нужна отдельно.

Точность автоматизации: выбранный CLI runner не заменяет конечный P1/P7 стенд. Batch/ubatch и sampler/seed/mode должны быть явно сохранены в command plan; локальный help проверяет поддерживаемые knobs. CPU/GPU placement подтверждается allocation logs, а не только намерением command line. Guest RAM/disk guards автоматические и sampled; host RAM/VRAM и physical VHDX coverage требуют внешнего/manual evidence. Отсутствующие counters/TTFT не превращаются в ноль или pass. Успешные synthetic tests подтверждают управление runner, а не llama.cpp compatibility или Windows производительность.

Quant acceptance: Q4/Q5 — исходные quality baselines, меньший GGUF quant не является автоматическим улучшением за счёт большего числа параметров. Q3 допустим только как optional опыт против меньшей модели Q4/Q5 на тех же patch/tool/RU/vision fixtures; фиксировать точные ошибки/структурные отказы и задержку, прекращать при провале frozen rubric. Q2 — самая низкая приоритетность, только при отдельной необходимости, не default/fallback. Это относится к weight quant; KV precision исследуется отдельной осью. [Unsloth Qwen3.5 quant research](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks), источник указан Org 28.10.2026, объясняет чувствительные tensors/mixed precision и пределы PPL/KLD как proxy; его результаты не выдаются за измерение качества Qwen3.8 или локальных задач.

Артефакт подготовки: [runner README](../../scripts/bench-offload/README.md). После последних safety правок writer завершил py_compile и10 synthetic tests; Planner проверил entry-point и интеграцию. Реальные модели не исполнялись. Наблюдения Windows/GPU/TTFT всё ещё требуют будущего target опыта.
